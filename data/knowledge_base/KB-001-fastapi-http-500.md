# FastAPI Endpoints Returning HTTP 500 Internal Server Error

## 1. Problem Overview

An HTTP `500 Internal Server Error` means the server accepted a syntactically valid request
but failed while producing a response. Unlike a `4xx` status, it makes no claim about the
client's request being wrong: the request may be perfectly legitimate and the defect is on
the server side.

In FastAPI the status is produced by Starlette's `ServerErrorMiddleware`, which sits at the
outermost position of the middleware stack. When any exception propagates out of the routing,
dependency-injection, or response-serialisation layers without being handled, that middleware:

1. Logs the exception and its traceback to the application logger.
2. Returns a deliberate, minimal response body (`Internal Server Error`, no traceback) so
   that internal paths, SQL, and variable values are not exposed to callers.

The generic body is a security property, not a bug. The useful information is in the server
logs, which is why the investigation in section 4 is log-centric.

Two distinct families of failure produce the same status code and must be separated early:

- **Raised exceptions** — code raised (`KeyError`, `TypeError`, driver errors, a failing
  `Depends` callable).
- **Response validation failures** — the handler returned successfully but the value does not
  match the declared `response_model`. FastAPI raises `ResponseValidationError` during
  serialisation, which also surfaces as a `500`.

Failure modes that look similar but are *not* 500s are worth ruling out immediately:
`502 Bad Gateway` and `504 Gateway Timeout` are generated by a reverse proxy or load
balancer, and `503 Service Unavailable` usually means the process is down or rejecting work.
If the body never came from your application, the investigation belongs to the proxy layer.

## 2. Symptoms and Typical Error Messages

**Characteristic response:** the body is the literal text `Internal Server Error`, and the
`content-type` is typically `text/plain` rather than `application/json`. A JSON body with a
`detail` field means a custom handler is installed and you are already in a better position.

**Characteristic server log:**

```text
ERROR:    Exception in ASGI application
Traceback (most recent call last):
  File "/usr/local/lib/python3.12/site-packages/starlette/middleware/errors.py", line 186, in __call__
    await self.app(scope, receive, send)
  ...
  File "/app/app/api/orders.py", line 41, in get_order
    return build_order_response(order)
           ^^^^^^^^^^^^^^^^^^^^^^^^^^
KeyError: 'shipping_address'
```

Response-model mismatch reads differently, because the traceback ends inside pydantic:

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for OrderResponse
total
  Field required [type=missing, input_value={'id': 7, 'amount': 2100}, input_type=dict]
```

or a `ResponseValidationError` wrapper naming the endpoint and the offending field.

**Observable patterns that narrow the cause:**

| Pattern | Strongly suggests |
| --- | --- |
| One endpoint fails, all others fine | Defect in that handler, its dependencies, or its response model |
| All endpoints fail | Startup/config problem, middleware, or a shared dependency |
| Fails only for certain payloads | Input-dependent branch, null handling, or schema mismatch |
| Started immediately after a deploy | Code, dependency, or migration change |
| Starts gradually under load | Resource exhaustion (memory, file descriptors, connections) |
| Intermittent, same request sometimes works | Race condition, cache/state, or one unhealthy replica |

## 3. Possible Root Causes

**Application logic defects**

- `KeyError`/`AttributeError` from a dict or object assumed to contain a field.
- `TypeError` from `None` where a value is required, often from an optional DB column or a
  `.get()` that returned nothing.
- Arithmetic on `Decimal` and `float` mixed, or division by a zero-sized denominator.
- Index errors from consuming a generator twice.

**Response contract defects**

- Handler returns a subset of the declared `response_model` (for example after a refactor
  that renamed a field).
- Field type mismatch: DB returns `Decimal`, model declares `float` with strict mode, or a
  naive `datetime` is required to be timezone-aware.
- Lazy ORM relationships are accessed after the session closed, raising
  `DetachedInstanceError` during serialisation rather than in the handler.
- `ORM`-mode models (`from_attributes=True`) pointed at an object lacking the attribute.

**Dependency and middleware defects**

- A `Depends` callable raises instead of using `HTTPException`; unhandled, it becomes a 500.
- A middleware raises outside its `try/except`, or re-raises after the response started,
  producing `RuntimeError: Response content longer than Content-Length` style errors.
- An authentication dependency returns `None` and downstream code dereferences it.

**Infrastructure-adjacent causes that still surface as 500**

- Database driver exceptions (`OperationalError`, `InterfaceError`) on a dropped connection.
- Missing or malformed configuration consumed lazily at request time instead of at startup
  (see KB-002).
- Disk full when writing an upload or log file; memory exhaustion leading to worker restarts.
- External HTTP calls whose failures were never mapped to `502`/`503`.

> **Version note:** the exact log wording and the exception classes raised for response-model
> failures changed across pydantic v1, pydantic v2, and recent FastAPI releases. Treat the
> tracebacks above as illustrative and confirm the class names against your installed
> versions (`python -m pip show fastapi starlette pydantic`) before grepping for them.

## 4. Step-by-Step Investigation

This section is **diagnostic only**. Do not change application behaviour until the failing
layer and the exact exception are known.

1. **Establish which layer produced the error.** Call the process directly, bypassing any
   proxy, to see whether the body comes from FastAPI:

   ```bash
   curl -i -sS http://127.0.0.1:8000/orders/7 -H 'X-Request-ID: diag-1'
   ```

   A `text/plain` `Internal Server Error` body means the app raised. A `502`/`504` with an
   HTML or proxy-specific body means the request never reached the app.

2. **Read the traceback, not just the status.** Search logs by the correlation ID you sent,
   or by the timestamp of the failing request:

   ```bash
   # Structured JSON logs: filter one request
   grep '"request_id":"diag-1"' /var/log/opspilot/api.log | tail -n 50

   # Plain uvicorn logs: pull the block around the error
   grep -n -A 40 'Exception in ASGI application' /var/log/opspilot/api.log | tail -n 60
   ```

   Identify the deepest frame in *your* package (`/app/...`), not in site-packages.

3. **Reproduce under a test client with exceptions enabled.** By default the test client
   re-raises server exceptions instead of converting them to a 500, which gives you the
   original exception type:

   ```python
   from fastapi.testclient import TestClient
   from app.main import app

   client = TestClient(app, raise_server_exceptions=True)  # default; be explicit when debugging

   def test_reproduce_500() -> None:
       response = client.get("/orders/7")
       assert response.status_code == 200, response.text
   ```

   > **Version note:** `raise_server_exceptions` is a `TestClient` option whose default has
   > been stable in recent Starlette releases but has been debated across versions. Pass it
   > explicitly so the test does not change behaviour after an upgrade.

4. **Reduce the request.** Remove headers, query parameters, and body fields one at a time
   until the request succeeds. The last removed element names the trigger (for example an
   optional field defaulting to `None` that the handler assumes is present).

5. **Separate "raised" from "invalid response".** Wrap the handler body in a temporary local
   probe, or call the function directly in a REPL, then validate its output against the
   model:

   ```python
   from app.api.orders import OrderResponse, get_order

   raw = get_order(order_id=7)          # does the handler itself raise?
   OrderResponse.model_validate(raw)    # does the value satisfy the contract?
   ```

   An exception here confirms a raised error; a pydantic `ValidationError` confirms a
   response-contract defect.

6. **Check whether the failure is stateful.** Repeat the same request several times. If it
   intermittently succeeds, suspect connection reuse, a closed session, a cache entry, or a
   replica with stale configuration rather than deterministic code.

7. **Inspect resource limits when the pattern is load-related.**

   ```bash
   # Container killed for OOM? Look for exit code 137 and restart counts.
   docker inspect --format '{{.State.ExitCode}} {{.RestartCount}} {{.State.OOMKilled}}' api
   df -h /var/log /tmp          # disk full breaks logging and uploads
   ulimit -n                    # descriptor exhaustion breaks sockets
   ```

8. **Correlate with change history.** Compare the first failing timestamp with deploys,
   dependency bumps, migrations, and configuration edits. A 500 that begins exactly at a
   deploy boundary is almost always introduced by that deploy.

## 5. Safe Troubleshooting Recommendations

These are remediation steps. Apply one at a time, after the diagnostics in section 4.

**Fix the root cause, then make failures legible.** Do not convert unhandled exceptions into
silent successes, and do not disable response validation to make a 500 disappear — that
trades a visible defect for corrupted API output.

- Correct the code defect at its source: guard optional values explicitly, adapt the query to
  select the columns the contract needs, and align the `response_model` with reality.
- For values that are legitimately absent, express that in the model (`field: str | None`)
  instead of catching exceptions at the edge.
- When a handler receives an anticipated failure, raise `HTTPException` with an appropriate
  `4xx` or `503` status instead of letting a driver exception escape. A downstream database
  that is momentarily unreachable is a `503`, not a `500`.
- Install one JSON error handler so clients and log pipelines always receive the same shape,
  with a correlation ID and no internal detail:

  ```python
  import logging
  from fastapi import FastAPI, Request
  from fastapi.responses import JSONResponse

  logger = logging.getLogger("opspilot.errors")
  app = FastAPI()


  @app.exception_handler(Exception)
  async def unhandled_exception_handler(request: Request, exc: Exception) -> JSONResponse:
      request_id = request.headers.get("X-Request-ID", "unknown")
      logger.exception("unhandled_error request_id=%s path=%s", request_id, request.url.path)
      return JSONResponse(
          status_code=500,
          content={"detail": "Internal server error", "request_id": request_id},
      )
  ```

  Register this only after confirming that the framework's default handler was not already
  supplying information you rely on. Never return `str(exc)` or `repr(traceback)` to clients.

- **Never enable debug tracebacks on a public deployment.** Debug pages and `debug=True`
  responses leak file paths, SQL, and sometimes secrets. Reproduce in a local or staging
  environment instead.
- Never "fix" a 500 by disabling authentication, TLS verification, or input validation.
  If a security check is failing, fix the configuration or the data it validates.
- If the trigger is resource exhaustion, raise limits only after evidence (heap profile,
  connection counts); otherwise the same failure returns at a higher load.

## 6. Verification Steps

1. The previously failing request returns `2xx` with the expected payload:

   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/orders/7
   # expect: 200
   ```

2. A regression test encodes the failing input, including the shape that broke:

   ```python
   def test_order_without_shipping_address_returns_null_field() -> None:
       response = client.get("/orders/7")
       assert response.status_code == 200
       assert response.json()["shipping_address"] is None
   ```

3. The error handler returns JSON for a deliberately triggered failure, and the log entry
   contains a traceback plus the same correlation ID the client received.
4. No internal detail appears in any client-visible response (`grep` the body for file paths,
   table names, and `Traceback`).
5. The full test suite and linter pass; a deploy to staging shows zero `5xx` for the
   previously failing route while the overall `5xx` rate is unchanged or lower.
6. The alert or dashboard that surfaced the issue returns to its baseline.

## 7. Prevention Strategies

- Type the whole request/response path, and validate response models in tests rather than
  only in production: assert against `response.json()` for the fields that matter.
- Treat `response_model` as a contract: change it and the handler together, in the same
  commit, with the test updated.
- Run static analysis (`mypy` or `pyright`) in CI so `Optional` dereferences fail before
  deployment. This catches the single most common 500 cause.
- Install error monitoring that captures exception type, stack, route, and request ID, and
  alert on the *rate* of `5xx`, not individual occurrences.
- Keep a correlation ID middleware and propagate it to logs; without it, incident triage
  becomes guesswork.
- Ensure sessions and clients are closed deterministically (`contextmanager` or dependency
  `yield` with `finally`) so serialisation never runs against a closed resource.
- Exercise error paths in staging: dependency failures, malformed rows, and downstream
  timeouts are the cases unit tests miss.

## 8. Related Technical Concepts

- ASGI application lifecycle and the middleware stack ordering (`ServerErrorMiddleware`
  outermost, `ExceptionMiddleware` innermost).
- `HTTPException` versus unhandled exceptions and the resulting status-code mapping.
- Pydantic v2 validation, `model_validate`, `from_attributes`, and serialisation errors.
- HTTP status semantics: `4xx` client faults, `5xx` server faults, `502`/`503`/`504` as
  proxy-generated statuses.
- Structured logging, correlation IDs, and log aggregation queries.
- Idempotency and retry safety when a `500` may have partially applied a write.
